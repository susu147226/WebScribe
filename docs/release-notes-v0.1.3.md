# WebScribe v0.1.3

本次更新解决「链接一多，界面就得一路滚动」的问题，并把固定的链接数量上限
改为可选档位。

## 新增

### 链接数量上限改为可选档位

原先固定为 10 条。现在可在界面上选择 **10 / 50 / 100**，默认为 50。

档位由主程序提供、界面直接渲染，两边不会各写一份而漂移；超限时的提示也改为
「请减少，或在上方调高上限」，并且**保留全部行的校验结果**，方便逐条处理，
而不是整批失败、无从下手。

> 关于数量：抓取对同一站点是串行的（同站请求间隔至少 1 秒），所以耗时下限由
> **同一站点最多的条数**决定，与总条数无关。100 条同站至少 100 秒纯等待，
> 且 100 次请求撞上限流或验证码的概率高于 50 次——程序会正确地停下来等待处理，
> 但任务可能只跑完一半。因此界面上会按同站条数给出最短耗时提示。

### 链接列表按文档分组合并展示

同属一份文档的链接收进一个可折叠的分组，组头显示分组名、条数、问题条数。

- **有问题的组自动置顶并展开**，其余收起——100 条里排查 3 条错误不必靠滚动去找
- 分组较多时默认只展开有问题的组；分组少时全部展开
- 新增「只看问题」筛选，一键过滤出格式错误与重复的条目

### 界面布局重做

| 项 | 变化 |
|---|---|
| 面板结构 | 改为三段式：顶部固定、中部列表独立滚动、**底部操作栏常驻** |
| 设置项 | 输出格式、图片处理、文档合并、抓取行为收进「设置」弹窗，让出约 545 px |
| 链接行 | 状态提示改为紧凑徽章（详情放悬停提示），行高由 **66 px 降至 39 px** |

改造前后对比（1200×900 窗口，101 条链接）：

| 指标 | 改造前 | 改造后 |
|---|---|---|
| 面板整体溢出 | 301 px（**零条目时**就已溢出） | **0** |
| 「开始抓取」可见 | 被卷出视野 | 始终可见 |
| 链接行高度 | 66 px | 39 px |

## 验证方式

本次没有依赖截图，而是**在真实渲染的页面上直接测量**，并用注入的桩造了
101 条链接（含 2 条格式错误、1 条重复、4 个文档分组）实测渲染结果：

```
[工具条] 共 101 条 · 4 份文档    只看问题（3）
[分组] ▾ developer.huawei.com/.../doc/content   1 条有问题  71 条   ← 问题组置顶且展开
[分组] ▾ 未归组                                  2 条有问题   2 条
       首行: 这不是URL    徽章: URL 格式不合法
[分组] ▸ example.com/docs/api                    20 条              ← 正常组收起
[分组] ▸ example.com/blog                         8 条
[底部] 尚未选择保存位置 选择 设置 登录站点 开始抓取
```

分组逻辑、默认展开策略、耗时估算已抽出为纯函数，并补了 17 项单元测试。

## 新增压测脚本

仓库新增 `tests/benchmark/`，用于日后调整档位或怀疑性能回退时复现：

- `scale.mjs` —— 按链接数量压测（10 / 50 / 100）
- `scale-large.mjs` —— 按页面体量压测（35 KB / 231 KB 每页）

实测结论：**内存与链接数无关**（50 条与 100 条的峰值完全相同，因为抓取是流式的，
每页抓完即推送、不累积）；**耗时严格线性，约 1.01 秒/条**，与页面大小无关。

## 其它

**启动日志记录版本号。** 每次启动会在
`%APPDATA%\com.webscribe.app\logs\` 写入一行：

```json
{"timestamp":"...","stage":"app-started","state":"WebScribe v0.1.3"}
```

排查问题时可以立刻确认对方跑的是哪个构建——此前遇到过一次「用户报告某问题、
但实际跑的是旧版本」的情况，靠比对可执行文件才能判定。
